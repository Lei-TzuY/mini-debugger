# v0.1.0 checkpoint

This document defines the first usable debugger milestone and the gates required before tagging `v0.1.0`.

## Baseline

Checkpoint candidate: `f3f1118ebb07c9d846e2de996e79e74766c2a407` (`feat: break on symbols across loaded modules`).

At this checkpoint the debugger already has a coherent end-to-end x86-64 Linux debugging path: launch/attach lifecycle handling, managed software breakpoints, register and memory inspection, signal policy, ELF symbol resolution with PIE/shared-object load bias, module-aware symbol/source breakpoints, DWARF v4 source mapping and source motion, bounded `.eh_frame` unwinding/`finish`, and cross-module symbol/source presentation.

The project is therefore entering a stabilization phase rather than continuing an unconditional feature-generation loop.

## Freeze policy

Until this checkpoint is released, do not add more isolated x86 call-encoding variants merely to increase decoder coverage. The existing `next` implementation is already acting as a small bounded instruction decoder; broader coverage should first introduce a deliberate decoder abstraction and direct decoder tests instead of extending an anonymous `if/else` chain one encoding at a time.

Allowed pre-release work is limited to:

- correctness regressions with a reproducible failing case;
- CI/build breakage;
- clear documentation or CLI inconsistencies;
- duplication or test-fixture cleanup that preserves behavior;
- release-blocking bugs found during verification.

If none of those conditions is present, the correct action is no-op.

## Release gates

Before tagging `v0.1.0`:

- [ ] `main` points at the intended release commit and its exact CI run is green.
- [ ] There are no open implementation PRs with release-critical fixes.
- [ ] `cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug`, `cmake --build build`, and `ctest --test-dir build --output-on-failure` pass on a Linux x86-64 environment where ptrace is permitted.
- [ ] README command list, architecture notes, and current-limit statements agree with the implementation.
- [ ] Existing source-`next` integration fixtures still cover the supported direct, ModRM, SIB, displacement, and REX forms without introducing new encoding-only slices.
- [ ] Stale merged feature branches and temporary branches are removed from the remote, keeping only branches that still represent active work.
- [ ] No release-critical TODO/FIXME remains in the traced-process lifecycle, breakpoint ownership, symbol/source resolution, stepping, or unwind paths.
- [ ] A short release note summarizes supported scope and intentionally unsupported features.

## Branch hygiene

The repository currently contains many merged `feat/*` branches plus temporary branches from the rapid implementation phase. They should be deleted after confirming their commits are reachable from `main`. Branch cleanup is repository hygiene only; history already merged into `main` must not be rewritten.

Future feature work should normally use one bounded branch/PR per roadmap milestone and delete the branch after merge.

## Automation policy after v0.1.0

Long-running automation should operate in sentinel mode:

1. re-check current `main`, open PRs, recent commits, CI/checks, tests, and active work;
2. prefer an existing implementation PR over creating parallel work;
3. fix a reproducible correctness regression or CI failure first;
4. otherwise select work only from an explicit Phase 2 milestone with a bounded acceptance test;
5. if no such gap exists, no-op.

The automation must not treat "produce a PR" as a success criterion.
